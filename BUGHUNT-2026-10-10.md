## Checked and clean
- Work lifecycle: 45,000 random steps (claims with/without leases, stale and held attempts, fail with/without retry, removals, re-joins, clock): at most one completion, done/failed exclusive, holders are current members, attempts never go down. Kept as `test/work-property.test.ts`.
- Permissions: 40,000 checks against an independent reference of "own capabilities cut down to the realm's": reads, posts, `targets`, `inbox`, `route-recent`. Kept as `test/permission-property.test.ts`.
- HTTP: auth (missing, bad, revoked, expired, lowercase scheme, token in query, Basic), routes, methods, body limits, malformed bodies, identity in the body ignored.
- Fuzzing every parameter of every op with 20 hostile values, as three different actors: no 500-class error left.

## Found, not fixed (decisions for the owner)
1. **Replay with a different payload is silent.** The same actor reusing a key (or the default key, e.g. `decide` on a decision already resolved) with different content gets the original event back and no error. `key-conflict` covers a different op or actor only. Stricter would be to store a hash of the arguments and refuse a mismatch; that changes replay semantics, so it was left.
2. **No size limits in Core.** A 5 MB post, a 1 MB title and a 3 MB work input are accepted over CLI/MCP/LocalCore; only HTTP caps the body (1 MB default). A limit per field in Core (for example 100,000 characters for text, 1,000 for titles) would close it.
3. **Work can be addressed to a non-member** (`--to human:nobody`); it can then never be claimed. Possibly intended (invite later), possibly a mistake.
4. **`decide` option check is new behaviour.** Free-text answers such as `yes, but only in staging` are now refused (`bad-answer`), including from a Pi agent's `DECIDE` command (it receives the refusal as feedback). If free text should be allowed, create the decision with an option list that says so.
